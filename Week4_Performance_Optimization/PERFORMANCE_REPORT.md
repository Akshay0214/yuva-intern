# Week 4 – Performance Optimization and Load Testing Report

## 1. Objective
The objective of Week 4 was to profile a backend API endpoint, simulate load conditions, identify performance bottlenecks, implement practical optimizations, and compare baseline and optimized implementations. The work builds on the Node.js, Express.js and MongoDB backend developed in earlier weeks.

## 2. Selected Endpoint
`GET /api/posts` was selected because collection/read endpoints can become expensive as data volume increases. The baseline returns the complete collection; the optimized version bounds the result set.

## 3. Baseline
The baseline uses an unbounded `find({})`, populates the author, sorts by creation time, and returns every post. Risks include growing database work, response size, serialization, memory use, and network transfer.

## 4. Optimizations
- Pagination using `page` and `limit`.
- Maximum limit of 50.
- Field projection for required fields.
- `.lean()` for read-only Mongoose results.
- `createdAt` index to support the sorting pattern.

## 5. Load Testing
`load-test/load-test.js` generates concurrent HTTP requests and measures total duration, success/failure count, error rate, throughput, minimum/average/median/p95/maximum response time, and average response size.

Recommended controlled run: 200 requests at concurrency 20. Use the same settings for both versions.

Baseline: `node load-test.js "http://127.0.0.1:3000/api/posts" 200 20`

Optimized: `node load-test.js "http://127.0.0.1:3000/api/posts?page=1&limit=20" 200 20`

## 7. Profiling and Bottleneck Analysis
The principal bottleneck is unrestricted collection retrieval. As the number of posts increases, returning every document increases database processing, serialization, application memory pressure, and network transfer. Pagination limits the amount of data processed per request. Projection reduces unnecessary fields, while lean reads avoid full Mongoose document hydration for read-only results.

## 8. Resource Usage
The supplied benchmark measures HTTP-level performance. CPU and memory measurements are environment-dependent and are not claimed unless collected during an actual run. They can be recorded using the operating system resource monitor or Node.js process metrics.

## 9. Limitations
This is a controlled local benchmark, not a production capacity test. Results depend on hardware, MongoDB dataset size, indexes, OS load, and network conditions. The same environment and database state should be used for a fair before/after comparison.
